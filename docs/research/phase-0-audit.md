# Phase 0: Home Assistant Integration Audit

**Audit date:** 2026-11-04  
**Scope:** Static review of the documented architecture, pipeline, missing-value and quality services, scheduler, service worker, database schemas available in the workspace, and PHPUnit tests. No scheduler, live Home Assistant request, or database write was executed. Local SQLite files were opened read-only for schema inspection; row contents were not read.

## Executive summary

The documented service pipeline is broadly recognizable in the source: `ProcessSensorData` maps entities, retrieves readings, calls cleaning and quality services, then writes sensor tables. The documentation is incomplete in several operationally important ways:

- The live page also fetches Home Assistant state and invokes the full ETL pipeline on a normal `GET`; it is not just a viewer.
- The service-worker timer is not a dependable daily scheduler. Its own comment acknowledges worker termination, but the stated client-side backup was not found in the repository.
- Completeness is calculated from readings that arrived, then assessed after cleaning. It does not account for expected samples with no row and can count interpolated readings as complete.
- The app stores a raw state string and separates `recorded_at` from database-default `fetched_at`, but does not persist the complete Home Assistant response payload. Its REST-history timestamp prefers `last_changed`, and may substitute the current time.
- Workspace-local SQLite files contain `api_states` and `api_events` schemas, but they are not tracked and no application writer for either table was found. The schemas alone cannot prove what their rows preserve. The app’s configured connection is PostgreSQL, as documented.

**First minimal, testable improvement:** make completeness count expected time slots for a requested period and report observed, explicitly missing, and imputed readings separately. This addresses the largest direct measurement error without changing the ingestion architecture; add focused unit tests before changing behavior.

### `api_states` / `api_events` payload and timestamp assessment

The workspace-local [home_assistant.db](../../database/home_assistant.db) schema has `api_states` columns for `state`, `attributes`, `context`, `last_changed`, `last_reported`, `last_updated`, and `fetched_at`. This is a structured snapshot with separate source-time fields and an ingestion-time field; it is not evidence that the full raw HTTP response bytes are retained. The app reads those columns in [api.php](../../api.php#L35), but no repository code was found that writes them.

The same local database defines `api_events` with `event`, `listener_count`, and `fetched_at`; it has no separate source-time column. A source timestamp could be present inside the `event` text, but no writer or sample rows were inspected, so payload fidelity and timestamp preservation cannot be confirmed.

The separate workspace-local [home-assistant_v2 1.db](<../../database/home-assistant_v2 1.db>) is a Home Assistant recorder-style SQLite schema, with source-time fields such as `states.last_changed_ts`, `states.last_updated_ts`, and `events.time_fired`. These local files are not tracked application migrations and should not be treated as proof of the deployed PostgreSQL schema.

## Prioritized findings

| Priority / severity | Finding and evidence | Minimal fix to consider |
|---|---|---|
| **P1 / High** | **Completeness misses absent records and can treat imputation as observation.** [DataQualityService.php](../../app/Services/DataQualityService.php#L35) sets `total_expected` to `count($readings)` and counts only rows with missing status or null value. The job assesses the **cleaned** array in [ProcessSensorData.php](../../app/Jobs/ProcessSensorData.php#L310); interpolation creates `imputed` rows in [MissingValueService.php](../../app/Services/MissingValueService.php#L194), which are not excluded from completeness. If a sensor emits nothing during a period, [ProcessSensorData.php](../../app/Jobs/ProcessSensorData.php#L286) returns without an assessment. | Derive expected slots from the selected period and an explicit sensor interval; report observed, explicit-missing, imputed, and absent-slot counts separately. Add tests for silent intervals, explicit `unavailable`, imputation, and period boundaries. |
| **P1 / Medium** | **GET routes have pipeline side effects; application-level access control is not visible.** [index.php](../../index.php#L22) routes `?page=live` to [api.php](../../api.php#L23), which fetches HA state and invokes `initSchema()` and `run()` for nonempty responses in [api.php](../../api.php#L72). The dedicated [scheduler.php](../../scheduler.php#L61) also runs the job on HTTP GET. It does restrict HTTP to loopback addresses in [scheduler.php](../../scheduler.php#L27), but there is no application authentication or CSRF protection in these paths. Whether a web-server layer adds protection is outside the repository evidence. A reverse proxy that presents loopback as `REMOTE_ADDR` would weaken the scheduler check. | Keep reads side-effect-free. Prefer a CLI/OS scheduler for writes; if HTTP triggering is retained, require explicit authentication/authorization and CSRF protection, and verify proxy/IP handling. |
| **P1 / Medium** | **Daily scheduling and repeat execution are unreliable/non-idempotent.** [sw.js](../../sw.js#L31) relies on a worker-resident interval, which can stop when the browser terminates the worker; its comment claims a client-side backup, but none was found. The timer has no retry or de-duplication, and [sw.js](../../sw.js#L46) does not check `response.ok`. Repeated job runs append readings in [SensorReading.php](../../app/Models/SensorReading.php#L102) and quality rows in [SensorQuality.php](../../app/Models/SensorQuality.php#L95), with no uniqueness key or run lock. Per-entity errors are returned in the job summary in [ProcessSensorData.php](../../app/Jobs/ProcessSensorData.php#L144), but [scheduler.php](../../scheduler.php#L65) still emits the result without setting a failure HTTP status. | Make the OS scheduler/CLI authoritative; add a per-period run lock and idempotent persistence or a run ledger; return non-success status when the run fails. Keep the service worker only as an explicitly manual/best-effort trigger. |
| **P2 / Medium** | **Missing record and explicit unavailable are not equivalent in the current pipeline, but only the latter is counted.** [MissingValueService.php](../../app/Services/MissingValueService.php#L28) classifies null, blank, `unknown`, `unavailable`, and `none` as missing; numeric zero is not missing and is covered by [MissingValueServiceTest.php](../../tests/Unit/MissingValueServiceTest.php#L18). In contrast, an entity with no history/state produces no reading or quality row in [ProcessSensorData.php](../../app/Jobs/ProcessSensorData.php#L286). `detectTimestampGaps()` exists, but active cleaning calls `imputeLinear()` directly in [DataCleaningService.php](../../app/Services/DataCleaningService.php#L51); interpolation only fills between numeric endpoints and does not fill leading/trailing gaps or bridge an explicit null endpoint. | Preserve explicit status/source and independently calculate absent expected slots. Avoid representing absence as `NULL` or `unavailable`; keep zero valid. Add tests proving each case remains distinct through persistence/assessment. |
| **P2 / Medium** | **Source timestamp and full raw-payload provenance are incomplete in the clean pipeline.** HA history is converted to `recorded_at` from `last_changed`, falling back to current time, in [ProcessSensorData.php](../../app/Jobs/ProcessSensorData.php#L233). The PostgreSQL fallback uses `last_updated_ts` at [ProcessSensorData.php](../../app/Jobs/ProcessSensorData.php#L252). The clean table has separate `recorded_at` and DB-default `fetched_at` fields in [SensorReading.php](../../app/Models/SensorReading.php#L51), but inserts omit `fetched_at`; attributes and original response JSON are not persisted by [DataCleaningService.php](../../app/Services/DataCleaningService.php#L65). | Carry source `last_changed` and `last_updated` distinctly (plus source timezone/precision where available), retain ingestion time, and persist the original raw payload or an explicitly defined lossless representation. Treat any schema change as a separately approved database change. |
| **P2 / Medium** | **Quality dimensions do not fully match their names/documented formulas.** Validity excludes `missing` and treats every other status except `invalid`—including `candidate_anomaly`—as valid in [DataQualityService.php](../../app/Services/DataQualityService.php#L57). Consistency is calculated over all sensors in [DataQualityService.php](../../app/Services/DataQualityService.php#L85), then copied into each entity assessment in [DataQualityService.php](../../app/Services/DataQualityService.php#L167). Timeliness estimates expected reports only between first/last observed readings and counts adjacent gaps up to 1.5 intervals as on-time in [DataQualityService.php](../../app/Services/DataQualityService.php#L135). | Publish metric definitions and denominators; decide whether anomalies/imputations qualify as valid, scope consistency per entity or label it fleet-wide, and calculate timeliness against period-based expected slots. |
| **P3 / Low** | **Current tests confirm helper formulas, not end-to-end scheduler or persistence behavior.** [SchedulerTest.php](../../tests/Unit/SchedulerTest.php#L12) reimplements date validation instead of invoking the scheduler; existing [DataQualityServiceTest.php](../../tests/Unit/DataQualityServiceTest.php#L19) tests observed-row formulas but not absent slots or imputed values. No API-state/event writer or schema integration test exists in the repository. | After the first metric change is approved, add tests at service boundaries and safe repository-owned seams; avoid tests that invoke live Home Assistant or the scheduler. |
